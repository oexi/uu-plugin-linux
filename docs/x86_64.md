# x86_64 (amd64 Docker image)

H3C has no x86 plugin, and NetEase's generic `openwrt-x86_64` plugin cannot accelerate PCs ([why](why-h3c.md)).
The `linux/amd64` image therefore runs the **aarch64 H3C NX30Pro plugin** under QEMU user-mode emulation (`qemu-aarch64`).
To the NetEase servers it is the same NX30Pro plugin as on an arm64 box.

Use it like the other images ([Docker image](docker.md)); nothing has to be set up on the host
(no `binfmt_misc`, no `qemu-user-static`). `uuctl status` and the log show `qemu 模拟运行`.

## How it works

- The image contains a static `qemu-aarch64` built from upstream QEMU with a small patch
  ([`docker/qemu/qemu-user-uu.patch`](../docker/qemu/qemu-user-uu.patch)), plus the aarch64 musl runtime from `runtime/aarch64`
  (`/lib/ld-musl-aarch64.so.1` → `/opt/uu/musl/aarch64`)
- `uu-monitor.sh` starts the plugin as `qemu-aarch64 ./uuplugin uu.conf` when `/opt/uu/qemu/qemu-<plugin arch>` exists;
  everything else (updates, gateway rules, DNS) is the same as on ARM
- Commands the plugin runs (`iptables`, `ip`, shell scripts) are x86_64 programs and run natively

## The QEMU patch

Stock QEMU is enough for the plugin to log in, but not for accelerating:

| Problem with stock QEMU | Effect on the plugin | Patch |
|---|---|---|
| `setsockopt(SO_MARK)` fails (unknown option) | Its own tunnel traffic cannot be marked to bypass its policy routing | Socket options QEMU does not know are passed to the kernel unchanged |
| `getsockopt(SO_ORIGINAL_DST)`, `getsockopt(IP_MTU)`, `setsockopt(IP_TRANSPARENT)` fail | Redirected (proxied) connections lose their original destination | Same |
| Netlink sockets other than route/uevent/audit (e.g. `NETLINK_NETFILTER`) are refused | Conntrack cannot be used if a plugin version needs it | Allowed, messages passed unchanged |
| A guest program exec'ing another guest binary needs `binfmt_misc` on the host | `uuplugin` cannot start `xuplugin-guardian` | `execve` of an aarch64 ELF re-runs the same `qemu-aarch64` (`qemu -0 argv0 path args`) |
| Emulated processes are named `qemu-aarch64` | `pkill -x uuplugin` and the monitor's process checks miss them | The process name (`/proc/PID/comm`) is set to the guest program's name |

Passing options and netlink messages through unchanged is correct here because aarch64 and x86_64 Linux share the
same ABI for them (little-endian, 64-bit, asm-generic socket option numbers); the patch is not meant for other guest/host pairs.

## Limits

- Emulation costs CPU: game traffic that goes through the plugin (tunnel / proxy) is handled by emulated code.
  Game traffic is light, but expect noticeably higher CPU use than on ARM
- Only the code paths used for logging in, setting up the firewall rules and the guardian have been verified;
  real acceleration under emulation has not ([Testing](testing.md))
- If the plugin uses something else QEMU cannot emulate, it shows up in QEMU's log: start the container with the environment variables
  `QEMU_LOG=unimp` and `QEMU_LOG_FILENAME=/tmp/qemu-%d.log` (one file per process) and look for non-empty files;
  `Passthrough ...` lines are expected and harmless
